# Epics and user stories

Generated by `python3 tools/build_docs.py`. S/M/L means small/medium/large relative complexity, not a calendar estimate. P0 = discovery/qualification; P1 = core; P2 = integrations/hardening; P3 = migration. Phase is earliest start, subject to dependencies.

Dependencies describe the complete target program. An external-only release uses its applicable profile gates; it does not require advertising or shipping unqualified native capabilities. Epic task lists and parent links express hierarchy; no native sub-issues or GitHub Project board is implied.

- **S3-CON: Falcone contracts and first-party scope** — Freeze existing behavior and ownership before replacing the storage backend.

  - **S3-CON-001: Freeze storage API and deployment contract fixtures** (P0, M)
    - As a Falcone maintainer, I want a pinned inventory of storage consumers and behaviors, so that the replacement preserves existing applications.
    - Description: A pinned inventory of storage consumers and behaviors.
    - Requirements: FR-S3-CON-001-1, FR-S3-CON-001-2
    - Dependencies: None
    - Acceptance: Cover console, SDK, workflow activities, runtime artifacts, presign, multipart, quotas and recursive product bucket deletion.
    - Acceptance: Resolve per-workspace versus per-bucket identity and tenant-versus-workspace quota documentation discrepancies using source fixtures and deployed evidence.
    - Acceptance: Record exact SeaweedFS/SDK versions, public/internal endpoints and any direct S3 users; identify unimplemented backup and capability-builder stubs.

  - **S3-CON-002: Define storage ownership and provider binding contracts** (P0, M)
    - As a platform architect, I want one authority for each bucket, object, policy and key, so that native and external modes integrate with Falcone.
    - Description: One authority for each bucket, object, policy and key.
    - Requirements: FR-S3-CON-002-1, FR-S3-CON-002-2
    - Dependencies: S3-CON-001
    - Acceptance: Publish binding and ownership schemas including managed/adopted modes and capabilities; changing a default affects new buckets only.
    - Acceptance: Use accepted falcone-secrets ADR 0002; do not create a second IdP, secret manager or quota-policy database.
    - Acceptance: Map provider changes to the migration protocol; no automatic fallback to an unrelated backend or shared-prefix allocation default.

  - **S3-CON-003: Qualify components, capacity assumptions and licenses** (P0, L)
    - As a maintainer, I want reviewed implementation choices and realistic demand measurements, so that the design fits restricted infrastructure.
    - Description: Reviewed implementation choices and realistic demand measurements.
    - Requirements: FR-S3-CON-003-1, FR-S3-CON-003-2
    - Dependencies: S3-CON-001
    - Acceptance: Evaluate TypeScript control and Go streaming paths with representative objects; do not infer S3 load from 100k event messages or 10000 deployed functions.
    - Acceptance: Identify approved storage classes, flush semantics, topology, database replication and namespace permissions; flag shared underlying storage.

- **S3-DATA: Native durability, repair and garbage collection** — Make storage acknowledgements and recovery trustworthy under the declared failure model.

  - **S3-DATA-001: Implement the staged-byte and transactional commit protocol** (P1, L)
    - As a storage engineer, I want explicit durable commit ordering, so that acknowledged objects survive the supported failures.

  - **S3-DATA-002: Implement qualified replication, scrubbing and repair** (P2, L)

    - Acceptance: Test domain loss, network partition, corrupt bytes, replacement worker and interrupted repair; reject writes when required acknowledgements are unavailable.

  - **S3-DATA-003: Implement reference-safe native garbage collection** (P1, L)

    - Acceptance: Crash and resume GC without deleting a newly referenced chunk or resurrecting a tombstoned object.
    - Acceptance: Provide a dry-run/evidence mode and metrics for reclaimable, blocked and actually reclaimed bytes.
